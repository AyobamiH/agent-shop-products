# Capability Surface Reconciliation

Produce a capability ledger before making a readiness claim or choosing the next tool.

## Recover the current authority

Read the newest authorised handover and repository decisions. Find the canonical repository, current branch, protected architecture and publication boundary. Treat an older recap as historical evidence until a newer observation confirms it.

Record the observation date, source, target and evidence limit. Keep owner reports, direct observations, public source and runtime readback distinguishable. If continuity retrieval fails, use the specifically supplied evidence without claiming that automatic recall worked.

## Inventory advertised surfaces

1. Read every page of each available skill catalogue. Keep cloud and executor counts separately.
2. Deduplicate by exact skill name for the distinct-name count; retain every provider surface. A duplicate name does not prove identical implementation.
3. Read the current tool registry. Record exact tool names and provider grouping, then account separately for orchestration controls outside that registry.
4. Note absent requested capabilities and owner exclusions. Registry presence does not override an execution restriction.
5. Save a dated, bounded snapshot. Refresh it after installation, connection or session changes rather than treating it as a permanent account inventory.

For public records, include metadata only. Exclude skill bodies, privileged tool instructions, credentials, internal package paths, account IDs and private examples. External skills and tools remain dependencies; inventorying them does not make them owned shop products.

## Reconcile independent states

| Axis | Evidence to seek | Limit |
| --- | --- | --- |
| Skill listed | Catalogue metadata | Does not prove the skill was loaded |
| Skill loaded | Observed instruction read | Does not prove a complete workflow |
| Provider discovery | Exact MCP discovery result | Does not prove exposure in this conversation |
| Session exposure | Current callable tool name | Does not prove account connection or execution |
| Connection and scope | Account-specific provider state | Does not grant authority for every action |
| Execution | Actual tool result on a named target | Does not prove downstream completion |
| Artifact or consequence | Readback of the resulting state | Does not prove independent customer success |
| Publication | Provider publication state | Does not prove adoption or commercial demand |

These are separate axes. An anonymous read-only tool may not need account authentication. Do not force every provider into one linear activation sequence.

Bind observations to package version, endpoint, account scope, input and time where available. Separate listing version, output schema version, source revision and deployed revision. Preserve unknown states.

## Resolve contradictory claims

Prefer the newest applicable observation, not simply the newest timestamp. A private test connection cannot replace a public installation test. An owner-account success cannot replace a fresh-account test. A merged change cannot replace runtime readback.

Retain earlier failures as history and mark the exact scope superseded by a newer success. When a call has an ambiguous side effect, read back its consequence before retrying. Do not probe unrelated signed-in sessions or bypass a blocked access path to fill the ledger.

## Map procedures to the shop

Compare each demonstrated procedure with existing product payloads and boundaries. Extend coverage for an existing product when it fits. Add a new original skill only for a distinct reusable workflow supported by reviewed work.

Keep product payload, metadata, provenance, capability inventory and commercial state separate. A coverage match does not claim that a product's skill was invoked. Preserve the repository's chosen interface; learning about MCP does not itself authorise an MCP server for the shop.

## Verify and hand off

Check counts, unique names, provider membership, complete pagination and projection consistency. Use a bounded read-only live call only when necessary and already authorised; record its actual result without upgrading the remaining axes.

Report: inventory scope and date; distinct skills and surface entries; registry tools and separate controls; directly exercised capabilities; absent or excluded capabilities; changed claims; next unresolved acceptance boundary.
